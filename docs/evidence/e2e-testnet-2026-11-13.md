Bugs this run found and fixed (with regression tests):

1. Resuming after the contract account existed demanded the full 6.5 NEAR again and refused with only about 5 NEAR left. It now requires only what is still to be spent plus a gas margin.
2. A freshly registered agent has `policy: null` on the live contract; the deploy tool crashed on it while the fixture used an empty policy object. The fixture now matches the live shape.
3. A dropped RPC connection printed only `UNEXPECTED_ERROR`; owner tools now say `NETWORK_ERROR` and to run the command again.

Not covered: the interactive `/connect` sign-in inside the full-screen app and a paid chat turn with this deployment.

## Owner pause signed by the key store (no NEAR CLI)

On the third throwaway deployment, `/pause` in the terminal (owner connected through the key store) produced a confirmed owner request with a transaction hash, and `/status` then read PAUSED. A direct `KeystoreWallet.send` of the same `set_paused` request after the broadcast code was simplified (one bounded attempt) was FINAL and successful on chain. `/pause` on an already paused agent correctly does nothing. `/resume-agent` refused by design ("Resume requires a verified current backup, ready restricted runtime and no local rotation hold"): this fresh agent has no verified backup, so resume through the key store was covered only by fake-RPC tests. That throwaway agent is left paused.

## Adversarial and payment tests on a fourth throwaway deployment (`persistara-sec-966315499.testnet`)

**Stolen runtime key, 9/9 refused for the right reason** (an attacker holding only the agent's restricted key): `set_paused` and `withdraw_funds` (key method list: `AccessKeyMethodNameMismatch`), transferring 0.01 NEAR, adding a key, deleting a key, deploying code (`AccessKeyRequiresFullAccess`), calling another contract (`AccessKeyReceiverMismatch`), attaching 0.01 NEAR to an allowed method (`AccessKeyDepositWithFunctionCall`), and checkpointing another owner's agent (`ERR_AGENT_NOT_FOUND`). Two of these first passed for the wrong reason (asked for more than the account balance); they were rerun with small amounts so the permission itself was tested.

**Pause stops the agent on chain:** a valid runtime checkpoint worked; the owner pause was signed by the key store; the same runtime key was then refused with `ERR_AGENT_PAUSED`.

**Real payment lifecycle on chain** (worker account `worker.<owner>`, runtime key, 0.01 NEAR job): over-limit job refused (`ERR_JOB_LIMIT`), unapproved worker refused (`ERR_WORKER_NOT_APPROVED`), accept before delivery refused (`ERR_DELIVERY_REQUIRED`), accept of a different result refused (`ERR_ARTIFACT_CHANGED`); after delivery and a correct accept the job was `paid` and the worker's balance rose by exactly 0.01 NEAR; a repeated accept paid nothing more; treasury accounting stayed conserved (deposited 0.1 = available 0.09 + paid 0.01). The owner resumed the agent directly with its key for this test (the client's resume gate was not involved).

**Code review** of `39f9e28..HEAD` found 10 issues; the valid ones were fixed with tests: the resume balance check now counts only unfinished steps, wallet failures reported by the signer are definite (only silence is unknown), the pause signer pins the workspace's contract and agent, the sign-in note follows the real path, the network-error wording is scoped to resumable tools, a no-op check was removed, and unexpected keys on the agent account make the runtime "not ready". Accepted as documented limits: rotation unsupported in agent-account mode (default layout), and an explicit `--wasm`/`--expected-hash` override can deploy the new layout against older code.
